日期只依据外层原生 # Task 行“Run: ... at <UTC ISO>”的触发时间。调用现成 bash 工具执行下面的一次只读输入检查，将 <UTC ISO> 替换为该 Task 的真实时间，保留双引号：
python3 -I /home/node/.config/opencode/daily_input_contract.py "<UTC ISO>"
它用 Python datetime/zoneinfo 计算触发时 Asia/Shanghai 日期的前一天，严格读取 report-inputs 中该日期的 JSON/Markdown，验证日期/窗口/repo/完成状态/错误数组/MD与JSON同次run，并返回结构化的完整开放Issue列表、PR列表、计数及数据质量字段；Markdown只用于核对同次采集，不重复返回长评论正文。不要执行其他命令，不读取环境变量、凭据或别的目录，不重复读取完整JSON，不用“最新文件”替代指定日期。

如果工具失败、缺时间、状态不是 READY，立即只输出“【AI辅助】日报等待事实数据”或“【AI辅助】日报输入校验失败”，附目标日期（能确定时）、本次 Agent Run ID 和真实原因。明确“本次未生成合格日报，需维护者检查采集或补报”；禁止猜数字、读其他日期、在同次run反复重试。注意底座保存这一等待/失败说明，并不证明事实日报成功。

READY 时，只以本次工具返回的结构化事实为准。open_issues是完整开放Issue清单，pull_requests是PR清单，必须分别逐项列出；counts、repository、snapshots、commits、ai_comment_count、ai_comment_threads、ci_runs和quality_notes分别供A—F使用。引用facts_report_url查完整原始评论清单。全局知识文件、项目说明、先前报告、记忆中的预览地址和测试结果均不是本日报的证据，不得引入。不能因为Markdown未返回就声称没有Issue明细。第一行为“# 【AI辅助】OntiCards 中文维护日报（目标日期）”。标题下逐行列：统计日期/Asia/Shanghai、完整窗口起点（含）/终点（不含）、采集时间、事实 run_id、本次 Agent Run ID；事实时间不等于任务触发时间，两种run编号不能混淆。

完整输出 A—F，简洁但保留所有已知事实和链接：

B Issue：先列目标窗口新增/关闭/重开数量，再逐项列采集时仍开放的 Issue 原文标题和链接。只有标题/元数据时每项写“待核实（分类暂不确定，需读取正文与相关代码）”及针对标题的下一步。咨询/缺信息/可修复缺陷/大改需人工是核实后的分类体系，不能强行四选一，也不能无新Issue就说无待办。
C PR：窗口新增/合并/未合并关闭/重开数量；每项明确是PR，保留原文标题、链接、完整head/base SHA及可用的mergeable/冲突/commit status/验证声明。commit_status_count只能称“传统提交状态条数”，绝不能写成Checks条数；GitHub Checks仅来自check_runs数组，null为未获取、空数组为0项，非空时逐项列name/conclusion及html_url/details_url。Check成功仅支持该Check报告的范围；本采集器不运行测试，不表示整个系统从未运行测试。缺失字段写未知；mergeable/clean不是测试成功，不作可合并结论。不凭相似标题推断PR关联或解决某Issue。
